# NCC 旧功能迁移调研报告（WCRobot → SiverWXbot_plus / wxautox4）

> 2026-07-05 · 结论先行：**大部分旧功能可以迁，且相当一部分上游已经自带**，我们要写的新代码比预想少。
> 真正需要自研的是三个插件级功能：**管理群转发、关键词拉群、迎新卡片**；
> 知识库**不需要也不应该放本机**（机器是 2011 年的双核 i5 + 8GB 内存），走云端 API，下文给了三档方案。

---

## 一、两代协议的根本差异（决定了迁移思路）

| | 旧协议 WCRobot（hook/iPad 协议类） | 新协议 wxautox4（UI 自动化） |
|---|---|---|
| 身份标识 | **wxid**，全局唯一、稳定 | **昵称/备注/群名**字符串，改名即断链 |
| 消息收发 | 协议层直接收发，快、可并发 | 模拟人操作 UI，一条消息秒级，串行 |
| 私聊入口 | 任何人可私聊触发 | 同样可以，但**加好友自动通过目前是坏的**（wxautox4 40.1.15 与微信 4.1.8.107 版本错配，5/13 起故障） |
| 转发 | 按 wxid 精准投递任意消息 | `msg.forward(targets)` 按名称转发，**支持一次转发到多个目标**，图片/视频/文件/卡片都行 |
| 风控 | 协议特征易封号（旧方案死因） | 行为与真人一致，存活性好 |

核心心法：**放弃"稳定 ID"这个执念，改用"受控的名称空间"**——群备注、好友备注都是机器人自己可以写的（`SetGroupRemark` / `EditFriendInfo`），把寻址权掌握在自己手里，改名断链的风险就可控了。

你提出的"拉一个管理群，群内成员即管理员"正好是这个思路的最佳实践：
- 旧方案靠 wxid 白名单验证管理员 → 新方案靠**微信本身的群成员关系**做鉴权，谁在管理群谁就是管理员，不需要任何私聊验证环节；
- 管理群是机器人建的（`CreateGroup`）、备注是机器人锁定的，寻址稳定；
- 转发素材直接发在管理群里，机器人 `AddListenChat` 监听即可，天然多管理员并发使用。

## 二、旧功能逐项对照

### ✅ A 类：上游已自带，配置即用（零代码）

| 旧功能 | 上游对应能力 | 备注 |
|---|---|---|
| AI 对话（@机器人 / "问："前缀触发） | 多 AI 平台接入 + 群"仅@回复"开关 + 关键词触发 | "问："可配成关键词触发；支持 OpenAI 兼容 / DusAPI / **Dify** / Coze |
| 每群不同的 AI 人设 | 多 Prompt 管理：每群/每私聊绑定独立 Prompt + 独立 AI 接口 | 旧版没有的能力，白赚 |
| 群迎新欢迎语 | 群成员迎新（新人进群自动欢迎，可带图） | 文本+图片版直接用；**卡片版**见 B 类 |
| 定时提醒（面板配置） | 自定义定时消息 | 上游是面板配置；`$time` 聊天指令式管理见 B 类 |
| 新好友自动通过 + 打招呼 + 自动备注 | 新好友功能（通过/欢迎语/备注前后缀） | ⚠️ 被版本错配 bug 卡住（见第五节阶段 0） |
| 消息转发（监听源→多目标，关键词/指定人/无差别三种触发，可带来源标注） | 自定义消息转发 | 这就是管理群转发的**地基**，我们只需在上面加"交互式选分组"一层皮 |
| 上下文记忆、消息去重、分段发送、回复延时 | 对话记忆 + 消息处理全家桶 | 旧版半残的功能，上游都做好了 |

### 🔧 B 类：换个方式变相实现（需要写插件，均有明确技术路径）

**1. "ncc" 管理员转发 → 管理群转发**（你的方案，可行且更优）

- 机器人 `CreateGroup` 建"NCC 指挥部"群，`AddListenChat` 监听；
- 管理员在群里发指令如 `转发 在地群`，插件进入"收集模式"，接下来该管理员发的任意消息（文本/图/视频/文件/链接卡片）由插件调 `msg.forward(target_list)` 一次性转发到该分组全部群——**wxauto 的 forward 原生支持多目标列表，不用逐群循环**；plus 版还能附加一条说明消息；
- 分组→群名映射存本地 JSON/SQLite（沿用 wechat_checkin 插件的结构），面板或群内指令维护；
- 风险与对策：目标群改名即转发失败 → ① 用**群备注**寻址（机器人定期 `SetGroupRemark` 锁定），② 加 `检查群组` 指令逐群 `ChatWith` 验证可达性并报告。
- 实现层面：完全照抄 `plugins/wechat_checkin/` 的"最小 hook + 插件目录"模式，不碰上游转发代码，合并上游无冲突。

**2. 关键词拉群（活动群 0→500）**

- wxauto 有 `AddGroupMembers(members)`：先 `ChatWith('活动群')` 再拉人，等价于旧功能；
- **推荐入口改成"群内触发"**：用户在任意已有 NCC 群里发关键词（如"报名灵感食堂"），机器人从该群把这个人拉进活动群——**绕开了加好友环节**，不受好友自动通过 bug 影响，而且群成员身份本身就是一层验证；
- 私聊触发路径保留，但依赖好友链路修复（阶段 0）；
- 已知边界：群 >200 人后邀请需对方点确认卡片（微信机制，旧协议同样如此）；拉人按昵称匹配，同名冲突时会失败——活动场景可接受，失败时机器人回话提示手动处理。

**3. 迎新卡片（在地化链接）**

- wxauto plus 有 `SendUrlCard(url, friends, message)`——直接把 URL 发成链接卡片，每群配不同链接即可复刻"黄山/大理/三亚/线上"在地化；
- 若"特殊版本链接"渲染出的卡片样式不满意，备用方案：把做好的卡片消息存在管理群/素材群里，迎新时 `msg.forward(新群)` 原样转发，样式 100% 保真；
- 触发点挂在上游"群成员迎新"的 hook 上（或插件自己监听系统消息"xxx加入了群聊"）。

**4. `$time` 聊天指令式定时任务**

- 上游定时任务是面板配置的；旧的 `$time 每天 08:00 打卡提醒 group[技术部] @all` 聊天指令体验可以做成插件：解析指令 → 写入上游定时任务配置（或插件自己维护 APScheduler）→ 到点 `SendMsg(msg, who=群, at='所有人')`（wxauto 的 `AtAll` / `at` 参数支持@所有人，需机器人有群管理员）；
- 管理入口放在管理群里，天然有权限控制。

**5. "肥肉"触发 + 拍一拍**

- 消息含"肥肉" → `msg.tickle()` 拍一拍发送人 → 再走 AI 回复。tickle 是 wxauto 现成方法，十行插件的事。

**6. 点歌**

- 旧版低频娱乐功能。可用音乐搜索 API + `SendUrlCard` 变相实现（发歌曲页卡片），优先级建议放最后，或直接砍掉。

### ❌ C 类：确认做不到 / 建议放弃

| 旧能力 | 原因 | 替代 |
|---|---|---|
| wxid 级稳定身份 | UI 层拿不到 wxid（签到插件已实测：私聊只有昵称/备注） | 管理群成员关系鉴权 + 机器人控制的备注命名空间 |
| 高频/并发收发 | UI 串行操作，一条消息秒级 | 转发用多目标一次成型；对时效要求高的走 webhook 通知（已有模块） |
| Notion 实时读配置 | Notion API 在这台机器的网络环境不稳（需走代理） | 见第四节：配置迁到面板/本地 JSON，管理视图如需协作改用**飞书多维表格**（NCC 团队已全面在用飞书，现成 lark 基建） |
| 成语接龙/新闻/天气 | 旧版已标记鸡肋关闭 | 不迁 |

## 三、知识库调研：不必在本机，也千万别在本机

### 本机跑不动（实测配置）

win-shukong 是 **i5-2520M（2011 年双核 4 线程）+ 8GB 内存 + C 盘仅剩 24GB**，且已经同时跑着：微信客户端 + wxautox UI 自动化 + Flask 面板 + WSL2（hermes 网关，WSL2 本身就吃 1-2GB）。任何本地 LLM 免谈；即使只跑 embedding 检索（bge-small + Qdrant 约再占 1-2GB 内存和常驻 CPU），也会挤压 UI 自动化的响应，得不偿失。**结论：知识库放外部，机器人只发 API 请求（几 KB 的 HTTP 往返，本机零负担）。**

### 推荐三档方案（按投入排序，可先 1 后 2 演进）

**① 零成本起步：把 NCC 事实直接放进 Prompt（本周就能上线）**

据点列表、主理人、各在地 WiFi 密码、肥肉人设——这些加起来就几千字，根本不需要 RAG。上游的 Prompt 管理就是散文件 `config/prompt/*.md`，直接建一个 `NCC肥肉.md` 把事实清单写进去，绑定到各群。信息变更就是改一个 md 文件（可写个小脚本从飞书表格定期拉取生成）。
- 优点：零新增组件、零延迟、答案可控；
- 边界：内容超过几万字（比如要吃下全部公众号历史文章）才需要升级到 ②。

**② 正式方案：Dify 知识库（上游原生支持，零代码接入）⭐推荐**

上游 AI 平台列表里**原生就有 Dify**。在 Dify（云端版 dify.ai，或自己 VPS 上 docker 一键部署——hkbohai / bh173 都够跑 Dify 社区版）建知识库应用：上传 NCC 公众号文章、据点资料，Dify 负责切片/向量化/检索/引用，机器人侧只是在面板里把 AI 接口切成 Dify 并填 API key。
- 优点：完整 RAG（能吃下全部历史文章）、有管理后台给非技术同学维护语料、机器人零代码改动；
- 注意：云端版走境外网络需机器上配代理；自部署在 hkbohai 这类境内可达 VPS 上最省心。

**③ 重型方案：自建 RAG 管线（OpenAI 兼容代理 + 向量库）**

即 epstein-kb 那套（RAG 代理 + Qdrant）的缩水版，部署在 VPS，对外暴露 OpenAI 兼容接口，机器人当成普通 OpenAI 接口接入。除非 ② 的检索质量不满足或有私有化硬要求，否则不建议为 NCC 这个体量上这套。

**问答链路（②为例）**：群友 @肥肉提问 → 机器人（上游 AI 模块）→ Dify API（检索知识库 + LLM 生成）→ 答案原路发回群。机器人本机全程只做转发。

## 四、管理台：Notion 还是搬家？

旧方案用 Notion 数据库当配置中心（群聊列表/分组/迎新链接/允许转发开关）。现状两个问题：Notion API 在境内网络不稳定（这台机器访问需代理）；且 NCC 团队的中台已整体迁到飞书（多维表格基建现成）。

建议：**运行时配置一律落本地**（JSON/SQLite，面板可视化编辑，机器人重启不依赖外网）；**协作视图按需同步**——如果团队仍要在表格里维护群分组，用飞书多维表格 + 每日/手动同步脚本拉到本地配置，Notion 页面转为纯文档存档。

## 五、分阶段实施计划

**阶段 0：地基修复与验证（先行，半天）**
- 升级微信 PC 到 4.1.9.x（需桌面扫码重登，你来操作），修复新好友自动通过——这是私聊类功能的前置条件；
- 建"NCC 指挥部"管理群，实测 `AddListenChat` + `msg.forward(多目标)` 对文本/图片/视频/文件/链接卡片的转发保真度（这一步的结果决定转发插件的细节设计）。

**阶段 1：管理群转发插件（核心价值，1-2 天）**
- `plugins/ncc_forward/`：监听管理群 → 指令解析（`转发 <分组>` / `分组列表` / `检查群组`）→ 收集模式 → `msg.forward` 群发 → 结果回报群内；
- 分组配置本地 JSON + 群备注锁定 + 可达性自检。

**阶段 2：迎新 + 拉群（1-2 天）**
- 迎新卡片：每群配置在地化链接，`SendUrlCard`（或素材消息转发）挂迎新 hook；
- 关键词拉群：群内触发 `AddGroupMembers`，私聊触发待阶段 0 修复后开启。

**阶段 3：AI 问答 + 知识库（1 天配置 + 语料整理）**
- 先上方案①（NCC 事实 Prompt），绑定各群、配好"@ / 问： / 肥肉+拍一拍"三种触发（拍一拍是个十行小插件）；
- 语料规模上来后平滑切方案②（Dify），机器人侧只改面板配置。

**阶段 4：锦上添花（按需）**
- `$time` 聊天指令定时任务插件；点歌；飞书表格→本地配置同步脚本。

每个阶段都遵守项目铁律：**业务进插件目录，核心文件只加最小 hook，不与上游打架**。
