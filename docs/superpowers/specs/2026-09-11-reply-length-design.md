# 回复长度自适应与中文标点（2026-09-11）

> 用户诉求：① 回复有时过短，对方想深入了解时应该展开；② 想过加「情绪感知模块」但担心多一层推理拖慢回复；③ 中文该用全角标点。
> 结论先行：**不引入任何额外 LLM 调用**。长度由两个「代码可判」的维度决定，标点由确定性后处理修。

---

## 1. 病根不是模型，是预算公式

`brain/gateway/shape.py::budget()` 现在是：

```python
预算 = 30 + 2.5 × 对方消息字数     # min 40, max 群 150 / 私聊 220
```

**自变量选错了。** 它假设「对方说得短 = 不想听长的」，而真实情况经常相反：

| 对方说 | 字数 | 现在给的预算 |
|---|---|---|
| 「展开说说」 | 4 | **40**（下限） |
| 「这个怎么做的？」 | 7 | 47 |
| 「NCC 据点在哪？」 | 8 | 50 |
| 闲聊灌水一大段 | 111 | **220**（顶格） |

**最想听详细回答的时候预算最小，纯闲聊写得长反而顶格。**

## 2. 实测数据（生产 mac-mini，2026-09-07~09-11，38 轮有效回复）

| 指标 | 数值 |
|---|---|
| 平均用满率 | 73% |
| **中位用满率** | **81%** |
| 用满 >90% 的轮次 | 8/38 |
| 预算 220（上限）那轮实际用量 | **218（99%）** |
| **跑了不止一轮（被退回重写）** | **20/38 = 53%** |

小预算几乎顶满：47→91%、55→94%、70→95%、77→100%、220→218。

**结论 A：给多少用多少。** 全局抬高预算 = 全面变啰嗦，所以必须「有条件地给」。

**结论 B：53% 的轮次在跑第二遍。** 每次退回 = 多一整轮完整 LLM 调用。
**现在这套卡死的预算本身就是最大的延迟来源**——放宽 + 少退回是净提速，不是变慢。

> ⚠️ 立项过程中曾用 mac 本机的测试日志（17 轮，全在测试群、松爸一人刷的）得出
> 「预算越大用满率越低、放宽不会话痨」的相反结论。**测试环境样本不能替代生产**，
> 上面这组数是 mac-mini 生产日志跑出来的，以它为准。

## 3. 标点：与预算无关，是模型的输出习惯

2026-09-06 全天真实回复统计：**半角标点 67 个，全角 0 个**。

验证过「是不是预算逼它用半角省字数」——**否**：`text_len()` 按字符数算，
`，` 和 `,` 都是 1 个字符，不省。人设里从未提过标点，模型就按自己的默认来了。

## 4. 外部调研

**主要参考：[The Chattiness Problem: Teaching an LLM When to Shut Up](https://blog.ax0x.ai/mio-chattiness-control)**（2026-03，中文人设 IM 机器人 Mio），它踩完了这条路：

- **硬 token 截断被否决**——断在半句比啰嗦更毁体验。
- **纯 prompt 指令不可靠**——"LLM 把长度指令当建议不当约束"。
  （与本项目 CLAUDE.md 3.16「人设里干写'不要用 Markdown'管不住」是同一个规律。）
- 最终方案是**双层**：每轮注入具体字数契约 + **亚毫秒的纯代码后处理，绝不多调一次 LLM**。
- 它的预算按「关系亲密度 × 话题深度」二维给，**不按输入长度**。
  疏远+短招呼 = 4 字/1 气泡；亲近+深度 = **84 字**/3 气泡；话痨人设 +15~40%。
- 效果：回复/输入字数比 5.02 → 2.78（降 45%），深度话题降 59%。

**模型自评长度档位不可靠**（这条否掉了「让大脑自己声明 depth」的初版方案）：
- **系统性漂向长档**：RLHF 长度偏好使模型把「长」等同于「有帮助」。
- **Verbosity Compensation**：内容不够时用重复、跑题、不请自来的补充填满空间。
- 模型缺乏对自身输出进度的感知，估不准自己写了多少。
- 建议**依赖行为信号而非模型自评**。
  来源：*A Long Way to Go: Investigating Length Correlations in RLHF* (arXiv 2310.03716)、
  *Demystify Verbosity Compensation Behavior of LLMs* (ACL 2025)、
  *Can LLMs Track Their Output Length?* (alphaXiv 2601.01768)。

## 5. 为什么不照搬「关系亲密度」这根轴

Mio 是**一对一伴侣产品**，亲密度是它的核心机制（有持久化数值、随互动累积），
"疏远 → 4 字"符合恋爱关系的渐进逻辑。**肥肉是社区机器人，照搬会反向：**

1. **人设明确要求相反的行为**——`PERSONA.md`「什么时候收着点」写着：
   > 新人第一次进群或明显刚认识你的人在正经提问：**先把事办了**，熟了再贫

   对新人要**更认真、把事说清楚**，不是更短。照搬会把「陌生人问据点在哪、多少钱」
   压到最短——正是 CLAUDE.md 3.7 记录过的事故类型（核心事实问题答不全，模型转头幻觉据点）。
2. **群聊场景里亲密度信号极弱**：一个群几十号人，每条消息发言人都可能不同。
3. **材料也薄**：生产 `memory/people/` 只有 5 个档案（113~342 字节）。

**保留 Mio 的骨架（二维分档 + 确定性后处理），换掉两根轴。**

## 6. 设计

### 6.1 两个维度，都由代码从「对方的消息」算出

模型**一个字的自评都不需要**，因此零漂移、零额外推理、零延迟。

**维度 A —— 办事 vs 闲聊**

判据（命中任一即「办事」）：
- NCC 事务关键词：种子取自 `mac-mini:~/ncc-kb/kb_keywords.txt`（117 行），
  抄一份进 `brain/gateway/errand_keywords.txt` 独立演进。
  **不跨机读那个文件**——它服务的是"要不要查知识库"，用途不同，硬合并会互相拖累。
- 技术名词（模型名、框架名、协议名等）。
- 问句形态：`怎么 / 多少 / 在哪 / 能不能 / 什么时候 / 为什么 / ？`

沿用 kb_keywords 的加词原则：**宁可宽松**。误判成「办事」的代价只是多给点额度；
判漏的代价是据点、价格、报名方式答不全。

**维度 B —— 对方想不想深入（强弱两档）**

判据全是**对方的行为**，不是模型的自评。回放生产日志后拆成了强弱两档：

| 档 | 判据 | 乘数 |
|---|---|---|
| `explicit` 强 | 明说要展开：`展开说/详细/细说/多说点/讲讲/举个例子/什么原理` | **×1.7** |
| `explicit` 强 | **办事类提问超过 60 字**——认真打一长段来问正事，本身就是投入度信号 | **×1.7** |
| `followup` 弱 | 在追问同一话题 | **×1.25** |
| 无 | 其它 | ×1.0 |

追问检测：从 `raw_hist` 取 `attr=="friend"` 且 `sender==` 当前发言人的最近 3 条，
判「共享事务关键词」或「2-gram 交集 ≥ 2」。复用 `shape.py` 现成的 `_ngrams()`
（原本用于反重复检测），零新依赖 —— **同一个工具反过来用**：反重复是"机器人别复读自己"，
追问检测是"对方在追同一个话题"。必须排除历史里与当前消息相同的那条，否则自己跟自己比必然命中。

**为什么强弱要分开**（回放生产日志抓到的）：
- 「@肥肉 以太坊现在什么价」因为前一条问过比特币而被判追问，×1.7 直接顶到群聊上限 150，
  **而它实际只值 51 字**。连续问币价是一串短问题，不是想听长回答。
- 闲聊+追问这一格的实际用量中位只有 **26 字**，给 ×1.7 会给到 87。

**为什么「为什么/为啥」不算深度信号**：日常问句里太常见。
「为啥吃寿司郎要排队呀？」曾被判成想深入、拿到群聊顶格 150，实际只值 37 字。
问原因归「办事」，深度只认明确的「多说点」类措辞。

**为什么长输入规则只对「办事」生效**：闲聊格的实际用量 max 只有 52 字，
灌一大段闲聊不该跟着放宽（旧公式正是在这里失手，给到顶格 220）。

### 6.2 预算公式

```python
预算 = (基数[A] + 0.5 × 入长) × 乘数[B]      # 夹进 [55, 群 150 / 私聊 220]
基数：闲聊 45 / 办事 85        乘数：常规 1.0 / 追问 1.25 / 明说要展开 1.7
```

入长因子从 2.5 降到 0.5：**保留「对方写了一大段说明投入度高」的弱信号，但不让它主导。**
（长输入的作用改由「办事 + ≥60 字 → 强深度」这条规则承担，见上。）

对比现状：

| 场景 | A/B 档 | 现在 | 新方案 |
|---|---|---|---|
| 「展开说说」（4 字） | 闲聊+强深 | 40 | **79** |
| 「NCC 据点在哪？」（8 字） | 办事+常规 | 50 | **89** |
| 追问「那大理具体什么价格？」（10 字） | 办事+追问 | 60 | **112** |
| 「大理的价格详细讲讲」（9 字） | 办事+强深 | 62 | **152** |
| 群里贫嘴一句（11 字） | 闲聊+常规 | 57 | **55**（下限） |
| 111 字长消息但只是闲聊 | 闲聊+常规 | **220（顶格）** | **100** |
| 111 字认真问策略 | 办事+强深（长输入） | 220 | **220** |

最后一行是「有时候废话太多」的真正来源：现在只要对方写得长就给顶格，而它会用掉 99%。

**这些数字是起始值，上线后按日志调。**

### 6.3 配套改动

**① 小幅超预算直接裁，不退回**（`validate.py`）

现在 `attempt < 2` 时一律退回让模型重写 = 多一整轮 LLM。改为：
- 超出在 **130% 以内** → 直接 `truncate_to()` 按句子裁到预算内放行，不退回；
- 超出更多才退回重写。

针对生产 53% 的重跑率，这是**净减延迟**。
按句子裁（现有实现）而非按 token 硬切，避免 Mio 踩过的"断在半句"问题。

**② 全角标点**（双层，与 `strip_markdown` 同一位置、同一道理）

- 治本：`PERSONA.md` 加一条，并**写明原因**（"半角在中文里显得生硬"）——
  CLAUDE.md 3.16 实测「把原因一起写上比干说一句管用得多」。
- 治标：`shape.py` 加 `to_fullwidth()`，在 `validate_reply()` 里紧跟 `strip_markdown` 之后调用。

  规则：**只转左右任一侧紧邻中文字符的 ASCII 标点**（`, ; : ? !` 及圆括号）。
  - `GPT-6:能力惊` → 右侧中文，转 ✅
  - `F1, 足球` → 右侧中文，转 ✅
  - `3.5` / `v1,2` → 两侧非中文，不转 ✅
  - URL → 复用现成的 `_URL` 正则先挖走再还原 ✅
  - 代码块内不转。

**③ 可观测性**（没有它就没法调参）

`replies-*.jsonl` 每轮加记：判定的 A 档、B 档、命中的关键词/信号、最终预算、实际用量。

> 现状缺口：日志里有 `attempts` 但**没记退回原因**，所以现在无法区分那 53% 的重跑
> 是超预算还是撞重复。本次一并补上。

### 6.4 回放验证（2026-09-11，生产 09-07~09-11 共 38 轮真实消息）

把生产日志里对方说的每句话按会话顺序重放一遍（历史逐条累积，模拟插件传来的流水）：

| 格子 | 轮次 | 预算中位 | 该格实用 max | 预算/max |
|---|---|---|---|---|
| 办事 | 18 | 92 | 101 | 0.91 |
| 闲聊 | 9 | 55 | 52 | 1.06 |
| 办事+追问 | 6 | 116 | 91 | 1.27 |
| 办事+强深 | 3 | 196 | 218 | 0.90 |
| 闲聊+追问 | 2 | 63 | 50 | 1.27 |

**装不下的轮次：旧公式 0 / 新公式 0** —— 没有回归。

原来最憋屈的那些短问题：

| | 旧 | 新 | 实际用了 |
|---|---|---|---|
| 「现在签到好了吗？」 | 50 | **89** | 33 |
| 「查查小红书呢？」 | 47 | **88** | 43 |
| 「好 小助手还没加我」 | 50 | **89** | 35 |
| 「在吗？」 | 40 | **55** | 18 |

标点：38 轮回复里 108 个半角标点 → 转出 105 个全角，37 条气泡被改写；
差的 3 个在 URL 和英文语境里，正确保留了半角。

> ⚠️ **口径提醒**：判断参数合不合适要拿「预算 vs 该格实用 **max**」比，不是比中位。
> 预算是上限不是目标，本来就该高于中位。中途用中位比过一次，得出「富余 60~140%」的
> 假警报，差点把参数收得过紧。
>
> ⚠️ **更重要的方法论限制**：上面这些「实际用量」是**在旧的紧预算约束下产生的**，
> 只能证明「新公式不会把该长的压短」，**不能证明「新公式不会让回复变长」**。
> 生产日志里预算 220 那轮实际用了 218（99%）—— 模型在宽预算下是会往上填的。
> 所以上线后必须按 §10 的指标回看。

## 8. 开关与回退

全部集中在网关 `config.json` 的 `budget` 段，**默认值即新行为**，但保留一键回退：

```jsonc
"budget": {
  "mode": "two_axis",        // 改回 "legacy" 立刻退回 30 + 2.5×入长
  "base_chat": 45,
  "base_errand": 85,
  "deep_factor": 1.7,        // 明说要展开 / 办事类长提问
  "followup_factor": 1.25,   // 只是在追问同一话题（弱信号）
  "long_input_chars": 60,    // 办事类提问超过这个长度，视同明说要展开
  "len_factor": 0.5,
  "min": 55, "max_group": 150, "max_private": 220,
  "overflow_tolerance": 1.3, // 超预算多少以内直接裁不退回
  "fullwidth_punct": true
}
```

## 10. 已知风险与未决

- ★ **最大的未知：模型在宽预算下会不会自己把话说长。** 回放只能证明新预算装得下过去的回复，
  证明不了将来的回复不会膨胀（生产有一轮预算 220、实际用 218 的先例）。
  **上线一周后必须回看**：拿 `budget_why` 分组，比较每格的「实际用量 / 预算」。
  若闲聊格的用满率明显往 90% 靠，说明模型在填预算而不是在表达内容 ——
  优先下调 `base_chat` 和 `min`，而不是动办事那一侧。
  人设里已写「预算宽不等于要写满」，但调研明确说过 prompt 层的长度约束不可靠，别指望它。
- **判据准确率未知**。上线后靠 §6.3③ 的日志回看一周，重点看两类错判：
  ① 该判「办事」判成了「闲聊」（据点/价格类问题答不全 —— 这是最贵的错）；
  ② 闲聊被判成办事（代价小，只是话多了点）。
- **维度 B 会漏**：对方没写关键词、也没追问，但确实想听多点 —— 这类给不了加成。
  这是「不用模型自评」的必然代价，接受。若日志显示漏得多，再议是否加回自评（届时必须带
  漂移监控：deep 占比超过一半即判失控）。
- **群聊场景验证不足**：生产 38 轮里只有 10 轮群聊。矩阵数值在群里是否合适，要单独看。
- **`min` 从 40 抬到 55** 会让最短的那类回复变长一点。若显得啰嗦就下调，不影响其它维度。
